# Focused context across repeated specialists

Use this when a child needs more information, returns after another specialist runs, or receives too much or too little context. The goal is enough relevant meaning for the current obligation, with explicit provenance and ownership. A narrow packet that omits a decisive qualification is incorrect; forwarding the whole transcript does not repair its contract.

## Contracts to design

Before minimizing context, map each specialist responsibility or acceptance criterion to the evidence needed to decide it: **criterion → required information → authoritative source → blackboard key → actual model input**. Include relevant original user wording, scope qualifications, conflicting observations, dependencies between returned artifacts, and the prior artifact when revising. A narrow contract that loses a decisive qualification is defective. A checker cannot reliably discover a requirement that was never supplied.

For a completion checker, provide the parent goal and acceptance criteria, actual artifacts being assessed, relevant evidence and its availability/version/limitations, unresolved questions, and projected receipts when completion requires effects. After parallel work, include the facts needed to assess interactions between results, not just each branch's self-reported success. Give a routing checker descriptions of eligible capabilities and what they can establish.

Distinguish satisfied, not satisfied, and insufficient evidence. If a required observation is missing, request it through a known resolver or preserve an explicit wait/handoff. A model confidence score does not supply that observation. Test context adequacy against independently stated task criteria, then inspect the final provider payload to prove transmission; schema validity and lower token count do not prove semantic sufficiency.

### Preserve comparison meaning and proposal identity

A scalar bound does not distinguish “after 16:00” from “at or after 16:00.” Have semantic intake return the literal bound plus a described relation, with explicit unresolved/absent handling. Preserve both through admitted state, owner packets and final evidence. Host guards apply the known relation; do not infer it with wording regexes or shift the timestamp.

Keep a rejected prior proposal and the current offer as separate records with their own identities and stages. A mutable current plan must not be exposed under a field named “prior proposal.” Pass the original message with the actual proposal it refers to, including any retained superseded request. Exact wire/canonical equality can faithfully transmit misleading labels; also inspect whether the writer relates these records correctly.

An unresolved relation needs a reachable clarification, wait or handoff path. A guard that refuses it and ends the root before the final writer prevents an unsupported action but does not deliver useful recovery. Verify that outcome separately from schema validity and successful known-relation cases. Retaining an uncertain interpretation as evidence need not grant effect authority: the [v4 continuation observation](context-evidence.md#conversation-qualified-uncertainty-v4) stored the original unresolved meaning, restricted effects for the current message/revision, and delivered a recorded clarification while preserving the completed sibling refund. Node success with a business-unresolved result was valid here. This bounded observation includes no later answer/resumption path; the owner's promise to proceed and the writer's unsolicited fee question remain limitations.

| Record | Meaning to retain |
| --- | --- |
| Goal/obligation | Stable ID, requested result, acceptance criteria, relevant original wording, constraints and current intent revision. |
| Specialist request | Fresh invocation ID, known capability ID/version, original obligation, local task and why it serves the goal, relevant prior draft, actual feedback and allowed effects. |
| Qualified evidence | Source ID, exact requested identity, observation/revision, availability, typed value and material scope/uncertainty/attribution qualifications. |
| Missing-information request | Request ID, requesting obligation/capability, precise question, blocking criterion, acceptable source/freshness, known answer contract and resume target. |
| Answer | Matching request ID; an attributable answer with source/revision, or explicit unavailability and its observed reason. |
| Specialist result | Matching invocation and obligation, actual artifact, completed/needs-information/unavailable/rejected outcome, new gaps, supporting evidence and observed effect receipts. |

Keep artifact and evidence versions where they can change. An observation, estimate and forecast have different evidential strength. Retain wording needed to interpret a short confirmation against a prior proposal. Keep irrelevant history and other specialists' private results out of the model's reads.

Keep model interpretations distinct from user-grounded constraints. An earlier model's unresolved classification or generated clarification question does not establish a condition imposed by the user. Preserve its original wording, message/event identity and inference provenance; keep genuine constraints separately tied to their authoritative source and current resolution state. A later answer must not silently discard a real condition, but uncertainty in a previous interpretation must not become a new user commitment merely because it was persisted. Preserve failed history without describing it as authority. The [bounded provenance observation](context-evidence.md#conversation-qualified-condition-provenance-v7) retained that history and produced an appropriate one-node interpretation with unchanged output instructions/schema. One new sample does not establish causality, general reliability, held-out condition retention or a repaired full continuation.

Give each specialist explicit ownership of its local criteria. The full parent goal supplies purpose and constraints; it does not make every child responsible for reassessing every sibling. Omitted sibling evidence means it is outside this child's view, not that the parent lacks it. If another criterion affects the child's own decision, provide that dependency's relevant current facts/status. The parent checker receives the actual joined artifacts and evidence. This prevents a focused child from incorrectly reopening already-completed work without forwarding the whole transcript.

## Current permission and a path to permission

An allowed-action set describes what may happen **now**; it does not explain whether a missing permission can be obtained or who can grant it. When a specialist chooses between asking, waiting and handing off, provide the actual authorization process: the permitted proposal scope, the required decision maker, whether consent can change eligibility, the host validation step and the resume target. Keep unknown grantability explicit. The model may propose or request permission; only the authorized host transition changes effective permission. Do not infer that process from an absent candidate or invent an exception path.

Assess continuation usefulness separately from effect safety. A tree can correctly refuse an unauthorized action, later resume successfully, and still fail the earlier turn by handing off instead of asking a resolvable question. Check the user-facing request and the waiting obligation, not only the eventual receipt. Give the writer and its checker the same delivery purpose and available next-step contract.

Advertised action meanings and current admissibility must agree with host transitions. A model can correctly understand the user's need and generate a useful question while choosing an action whose documented meaning fits but whose host guard forbids it. Describe the distinction between gathering clarification, recording an exact approval proposal and applying an effect; carry current eligibility and the specific rejected invariant back to the responsible owner. Do not rely on parsing error prose or force a case-specific route. Verify that the chosen question is recorded in the durable form needed for its later answer, not merely emitted by a writer. The [held-out dialogue audit](context-evidence.md#conversation-heldout-condition-v8) observed three useful exact-choice questions labeled as offers that a clarification-required host refused; the final honest unresolved reply did not create a resumable request. That observation identifies a contract mismatch. A subsequent [audited same-case development regression](context-evidence.md#conversation-clarification-contract-v9) changed three action/authority/question descriptions and completed clarification, conditional preference, exact approval and one fresh-zero-fee-quote-bound move while retaining the refund. All eleven calls matched canonical inputs/outputs and response identities. Preserve the original V8 failure: this was not a fresh held-out success or general reliability proof, and the initial intake still incorrectly classified ordinary consent uncertainty as an unresolved qualification. The live approval intake itself retained the genuine fee condition; independent host retention when the current interpretation says none is supported only by the separate typed offline control. A later [audited fresh wording-and-slot transfer](context-evidence.md#conversation-fresh-transfer-v10) reused that repaired code unchanged for a new three-message case and completed the same clarification, conditional preference, exact approval and quote-bound effect with the refund unchanged. All55 generated fields, eleven full input packets and eleven response IDs matched canonical records. This supports one fresh transfer within the fixture domain, not general condition resolution or statistical reliability; the initial writer's promise could still blur preference clarification and effect approval, and the historical qualification misclassification remains unresolved.

### Apply the authority-transition contract

When permission may change during a task, map the following facts to declared input keys before assembling the tree:

| Fact | Authoritative source | Model consumers |
| --- | --- | --- |
| What may execute now, with applicable revision | Current host authorization state | Action owner; writer and checker when describing current options |
| What may become permitted, and any prohibition or unknown eligibility | Actual policy, including its effective scope | Owner, writer and checker |
| Who can supply approval and what must be approved | Policy and the specific pending proposal | Owner, writer and checker |
| How approval is recorded and revalidated | Host command/adapter contract | Owner; writer and checker need the user-relevant prerequisite, not internal implementation prose |
| Original obligation, pending request and resume target | Application continuation state | Resumed owner; writer and checker when describing remaining work |

Inspect each consumer's serialized provider request for those facts and their meanings. A field existing on the root blackboard does not prove the child or checker received it. Keep the proposed permission request separate from the validated permission state. Check that a proposal alone cannot authorize an effect, and that a prohibited alternative remains prohibited even when a user asks for it.

Separate selecting a desired action from authorizing its execution. If selection can only return actions already authorized, the tree may have no way to propose a useful action whose prerequisite is customer approval. Let the specialist propose an action within the described capability and policy scope. Host code then evaluates the exact proposal's prerequisites. A missing required approval becomes a durable pending dependency; a prohibited action remains prohibited. Neither a model verdict nor a broad `partial` outcome may waive the action's authorization contract.

A reply to an approval can also change the requested action. Carry the addressed proposal as historical context and advance the current requirement revision when the host accepts the replacement. Bind any later consent to the new proposal. A terms specialist can return a fresh observation to the original owner while the independent completed effect remains in its own receipt. In the controlled SQLite proof, a changed fee blocked the move after exact approval and the prior billing receipt survived. The hosted interpretation of the combined reply remains open. Conversation proof (historical local experiment; private archive not bundled)

A later fresh-author workshop case completed live on Luna and MiMo with unchanged prompts, contracts and authority logic and common hosted token/deadline settings. Both models replaced a pending time proposal without premature booking, classified later conditional consent, retained one credit and let a fresh terms observation block the changed-fee booking. All 12 responses matched 48 canonical fields. These are two-model results on one case and its adverse variant; local services were synthetic. Matched live results (historical local experiment; private archive not bundled)

Bind the pending dependency to the original obligation, exact proposed arguments, required approver and governing policy. Validate the answer against that dependency, then revalidate current authority at execution. Preserve already committed effects separately. Recording a pending dependency does not prove that its question was delivered usefully: give the writer and checker the actual proposal, user-facing purpose and answer requirements, and inspect the emitted question before claiming successful waiting.

The context-only live checkpoint transmitted the transition policy correctly but still ended partially without establishing the pending step. Source inspection found selection restricted to currently authorized effects. This supports checking both context and reachable tree paths; it does not establish general consent-intake behavior or prove that any one prompt phrase caused the choice. Validate the complete proposal, prerequisite, delivery and resume path in the consuming application.

## A concrete missing-information shape

This illustrative contract uses a finite known answer contract, not a model-generated Malli schema. Change its domain-specific answer kind and source scope to the actual catalog. Every name and description is part of the contract.

```clojure
(def missing-information-schema
  [:map {:closed true :description "A question that blocks a specific existing obligation"}
   [:request-id [:string {:description "Stable identity linking this question to its answer"}]]
   [:obligation-id [:string {:description "Original goal obligation that must resume"}]]
   [:requester-id [:string {:description "Known specialist that needs the answer"}]]
   [:question [:string {:description "Precise missing fact; do not substitute a general research topic"}]]
   [:blocking-criterion [:string {:description "Why the original goal cannot yet be accepted"}]]
   [:allowed-source-ids [:vector {:description "Eligible source identities from the host's actual catalog"} :string]]
   [:freshness [:string {:description "Required observation period or revision and why it matters"}]]
   [:answer-contract [:enum {:description "Registered typed answer expected by the requester"}
                      "source-observation"]]
   [:resume-target [:string {:description "Known specialist to revisit for the same obligation"}]]])

(def evidence-answer-schema
  [:map {:closed true :description "Actual answer or observed reason the question remains open"}
   [:request-id [:string {:description "Identity of the missing-information request answered"}]]
   [:availability [:enum {:description "obtained contains evidence; unavailable preserves the actual blocker"}
                   "obtained" "unavailable"]]
   [:source-id [:string {:description "Exact source actually attempted, checked against the request"}]]
   [:revision [:maybe [:string {:description "Observed source revision; nil when no observation was obtained"}]]]
   [:observation [:maybe [:string {:description "Actual source observation, not a guessed default"}]]]
   [:qualification [:string {:description "Material scope, uncertainty and attribution limits"}]]
   [:unavailable-reason [:string {:description "Observed blocker when unavailable; empty for obtained evidence"}]]])
```

Validate dependent invariants too: `obtained` requires an observation and its applicable revision; `unavailable` requires its actual reason. Schema validity alone does not establish those meanings. Use native structured facts instead of the string observation when the source provides typed fields.

## Resolve, then resume

1. A returns a typed request alongside its useful partial draft. Keep A's original obligation open.
2. The parent selects an eligible answer source or known resolver B using the request's meaning and described capabilities. Code validates selected IDs and permitted effect scope.
3. Bind B's actual answer to the request. Verify returned source identity against the selected source, on every attempt; preserve its qualifications and availability.
4. Construct A's **new** invocation from the original goal, prior draft, actual feedback and matched answer. Include the question being answered, so A need not rediscover why B ran.
5. Reconcile A's current result only. Match invocation/obligation and revision, then update that obligation. Do not sweep stale per-specialist keys into the result or replay completed effects.

If no capability can answer, keep the useful partial artifact and precise gap in the durable business handoff. If the user must supply information, the application owns that wait and its later resume trigger. A successful handoff is not an achieved original goal. This contract does not imply automatic persistent conversational memory or process restart recovery.

A specialist may correctly return no operations or edits because the required source has not been observed. Represent that as a valid business outcome with its actual reason, rather than forcing an invalid item or treating it as a schema failure. Carry the specialist's exact work request and explanation, with invocation/obligation identity, through the child's declared return into the owner's next input. A generic host message such as “no replacement proposed” loses the information needed to choose a useful next step. A rationale preserved only in a trace is not model-visible feedback. Inspect the next owner's actual provider packet to establish that the explanation arrived; then assess whether its chosen observation addresses the missing evidence. Keep a host/tool setup failure separate so it cannot masquerade as an unmet task requirement.

| Omitted input versus nil | A delegate's declared missing read can become nil in the child. Use `[:maybe concrete-schema]` for a legitimately absent value or a route that does not pass it. `{:optional true}` describes omission; it does not make nil a valid map. |
| Code return | Every declared write must exist and be non-nil on success, including negative/waiting branches. Prefer one typed result envelope when branch fields differ; put optional fields inside it. |

## Planned effects are not observed effects

A generated draft can correctly describe a proposed action and still falsely say that action has already happened. Keep permitted effects, planned effects and projected receipts distinct. Before persistence, a briefing is prepared; the writer and checker must not treat a forthcoming recording command as an observed receipt. If post-commit prose needs to describe a completed effect, give that later node the actual command/query result and stable identity. A successful later write does not retroactively make an earlier checker input accurate.

Inspect effect claims in the actual text against the receipts available at that exact invocation. Explicit instructions and an empty observed-effects list alone did not prevent premature recording claims in a live authored workflow; a finite checker accepted the final draft despite that claim. This is a semantic acceptance limitation, not evidence of a parser failure. Keep the original response and distinguish verified task facts from complete factual accuracy.

## Current artifacts and historical feedback

Pass current artifact identities explicitly when a specialist is revisited. Preserve the previous artifact as history, but identify which accepted invocation now represents each obligation and which invocation it superseded. Attach critique to the artifact it actually assessed. When the replacement is accepted, label critique of the old artifact as historical instead of leaving the synthesizer to guess whether both remain active.

Keep actual source revisions separate from artifact invocation identities: new evidence does not itself revise an artifact. The owning specialist must interpret it, return a fresh matching result, and have that result reconciled into current state. A parent checker then receives the accepted current artifact plus relevant qualified source evidence. A code transform can establish these identities and relationships; it must not manufacture semantic acceptance or erase unresolved critiques. If feedback concerns synthesis rather than a specialist artifact, define its own subject/revision before claiming the same provenance guarantee.

Keep provenance available to the model and durable evidence without requiring it in reader-facing prose. Put invocation IDs, supersession relationships and receipts in structured diagnostic fields; include them in the narrative only when they help its reader. Preserve the actual artifact unabridged in evidence. A proposed draft can remain stored as an artifact of its pre-commit stage, with a separate receipt establishing the later effect; avoid rewriting its historical stage to imply the earlier checker saw a receipt.

### Bind unambiguous host correlation outside semantic generation

When owner, goal revision and answered-question identity already follow unambiguously from an admitted child request, construct that correlation in a separate typed host result envelope. Keep the actual artifact, explanation and newly needed facts as model work. Capture the admitted packet under its actual execution identity, then revalidate that packet against trusted lineage and current authority immediately before binding and installation. Preserve the domain guard that rejects stale, foreign or mismatched envelopes. A latest shared context or a model-returned owner is insufficient authority.

This changes which producer owns the fields; it does not fill missing generated data with a template. A field the model must actually choose, such as a source citation, remains an explicit validated semantic selection. Keep both model writes and the host envelope inspectable in canonical traces. A normal invocation may omit consultation identity; a resumed invocation binds the actual recorded question from its own admitted packet.

### Citation scope belongs to the analysis's own invocation

When one analysis schema appears in new owner/method output and nested historical priors, describe citations relative to **that analysis's own invocation**. Newly generated supporting IDs must come from the actual observations in its owner or method input packet. A nested prior retains its original citation set and qualifications; seeing it does not enlarge the new invocation's current citation set or dependency basis. Preserve useful historical explanation while keeping the current-observation guard. An observed unavailable result can support a claim about retrieval status, not missing artifact terms.

### Reconciliation includes host procedural feedback

Update host procedural feedback in the same accepted transition that installs the matched owner's finding and consumes its pending consultation. A message still saying the owner must reassess contradicts the now-current finding and cleared pending state. Keep that message while genuinely pending; an unrelated owner must not consume it. The replacement feedback reports the procedural transition only, not semantic support, authorization or an external effect. Give writer and controller the accepted finding and actual reconciliation state; a generated draft's account of that history is a claim to check against them.

The [bounded consumer checkpoint](context-evidence.md#investigation-consumer-contract-checkpoint) verifies these distinctions and retains the earlier failures. It does not establish that stale feedback was their sole cause.

## Audience and purpose are part of the output contract

Before a writer runs, define who consumes each output and what they need to decide or do. A specialist artifact may serve another specialist; a final explanation may serve an operator or end user. Describe that purpose on each output field, and pass a typed audience/delivery brief when it varies by invocation. Include relevant tone/detail constraints, required qualifications and effect stage. The writer still needs sufficient evidence; audience context is not permission to hide uncertainty.

Separate reader-facing explanation from structured continuation state, diagnostics and provenance where their consumers differ. Let the model author the explanation with those responsibilities visible. Do not strip IDs, caveats or unwanted phrases after generation with regex or fragile cleanup. If a draft fails its intended audience or meaning, assess the actual draft against its delivery brief and evidence, then give its writer focused feedback within the existing bounded repair path. A separate presentation specialist is useful only when it has a distinct reusable responsibility; audience awareness does not require another node in every tree.

## Separate model context from execution history

A public execution result can contain the full blackboard and execution metadata, including the original input. When carrying a node's generated work forward, select its declared writes rather than storing the entire execution envelope as another model result. Preserve canonical inputs, outputs and execution identifiers in the durable trace.

Build the next model input from its responsibility: current artifacts, any distinct prior revision needed for critique or continuation, the unresolved question, actual tool observations, qualified sources and described eligible capabilities. A chronology can reference artifact and invocation IDs already present in that packet. Do not serialize the same full artifact again in a result wrapper, historical entry and current-artifact map. Removing duplicate representations is a structural projection; it must not truncate or rewrite model-authored content, erase unique evidence or turn a superseded artifact into the current one. If revision history itself is the task, include those distinct revisions explicitly.

Inspect the final serialized request, including escaping and catalogs. A local conservative byte-admission limit is distinct from provider-reported tokens and the model's context window. Record the actual rejecting boundary before diagnosing model capacity. Context sufficiency is criterion-to-evidence coverage, not merely a smaller prompt.

Reuse needs a validity policy for the outcome being reused. Source revision equality alone does not show that a formerly unavailable source is still unavailable. If an unresolved result should be retried, include availability observations, a freshness deadline or an explicit re-evaluation trigger in that policy. An application preflight that returns a prior record proves application reuse; distinguish it from a BT success condition or a resumed interrupted tick.

## Material questions and evidence access

For a checker deciding whether to stop, map each material criterion to current artifacts, authoritative observations, relevant resolver capabilities and observation state. Missing from this packet, not yet requested, observed unavailable and superseded are different states. A critic without capability context can incorrectly conclude that a truthful limited summary is the completed task. Pass the same relevant evidence-access facts to critic and router, while keeping unrelated catalogs out. Read [evidence closure](../../orc-design-tree/references/evidence-closure.md).

Keep pre-action assessment and actual effect outcome distinct. Preserve the proposed artifact verbatim with its phase and identity, then attach the actual command receipt/current projection. If the proposal says an effect has not yet happened, do not reuse that text as the authoritative post-action state or fix it with string replacement. A recipient should be able to distinguish preparation from execution from typed fields.

## In-flight work and completed-turn state

A persisted turn counter, an active invocation revision, an artifact revision and an effect receipt revision are different identities. Describe each precisely. During a turn, an effect may already be committed while the completed-turn counter has not advanced. Supply an immutable invocation context with the active revision and prior completed revision; do not describe a mutable working snapshot as uniformly historical. Validate receipt identity against the actual authorized projection in code. A counter mismatch alone is not a semantic failure.

Keep pre-action model analysis under an explicitly historical proposal field. Supply the actual observed effect state and matching receipt separately after the command. A checker must not mistake “not yet executed” in an old proposal for the current state. Do not rewrite the proposal or invent a replacement explanation.

When claiming no duplicate or missing effect, describe the scope and completeness of the queried ledger. An omitted receipt in a partial packet does not prove absence. Exact ledger counts/identities can be host-derived facts; whether those effects satisfy the user's current request remains a semantic judgment. Pass relevant current observations to the final writer and checker as well as the action specialist.

## Effective policy is not merely a document revision

When validity depends on policy, consent, time or source replacement, provide the actual governing version/effective interval and its authoritative origin. A document mentioning what a future revision would revoke does not establish that the revision is active. Preserve conditions as conditions until their triggering facts are observed. Describe document revision, effective policy revision and artifact revision separately.

If new evidence changes a material dependency, explicitly mark the owner's prior artifact as needing reassessment and carry its actual supporting observations into the next invocation. A critic or synthesizer must not silently declare old specialist state repaired. If independent direct evidence makes a stale statement immaterial, retain that scope distinction; do not discard the provenance. These contracts reduce ambiguity but still require a live semantic probe: an earlier source-complete investigation misinterpreted conditional revocation and its later checker accepted that wrong interpretation.

Distinguish an interpretation from a committed effect when defining invalidation. Changed governing evidence can require a new specialist assessment, while an effect validly committed under prior authority remains a historical fact. Do not replay or erase that effect solely because current policy changed. Any reversal needs its own authorized behavior. Check both cases through current observations and immutable receipts; retaining a receipt is not permission to reuse an outdated interpretation.

Derive a concise instruction from it when useful, while passing the relevant original fields to the responsible specialist. Equal request prose can describe different subjects or constraints; compare the complete meaningful goal before treating an old artifact as current. Keep evidence-view changes separate from user-goal changes so healthy independent work can survive the former.

Bind a returned finding or consultation to the original goal and owning invocation before recording it. Preserve that goal in the durable helper response and the receiving owner's next packet, rather than assuming a matching source ID proves matching authority. A report draft also needs the current goal and evidence-view identity; those checks alone do not prove that its complete finding basis is still current.

## Durable continuation state and focused model packets

Runtime capabilities reconstruct access to providers, tools and stores; they do not reconstruct authoritative progress held only in a process atom. For an authored tree whose continuation state belongs on its blackboard, carry a concrete typed host value through declared code/delegate reads and writes. Project each model's focused packet from that state; making progress durable does not require sending the whole host state to every model or changing its output contract. Application-owned domain state can instead live behind commands and projected queries. Choose the owner deliberately rather than requiring a host snapshot for every leaf.

Parallel children receive isolated inputs and return their owned artifacts. Join those artifacts explicitly before replacing parent continuation state; concurrent branches should not each overwrite a shared whole-state snapshot. On a revisit, preserve the current invocation, matched consultation, consumed work and healthy sibling artifacts. Resolve actual forwarded values through the pinned runtime's public value-log APIs. A raw latest-value map or an invented helper alias can miss child references even when the events are present.

Verify the consuming leaf's exact declared inputs as well as its engine start metadata. Those are different views. Likewise, a value-write source ID is not necessarily the producing node's completion-event ID. Trace the actual source event, execution context and value instead of comparing unlike identifiers.
