Historical grill base: `checkpointed-resumable-repl-researcher` @ `386cb400`. Current implementation base: merged `main` @ `1b6f95cb`, including PR #36 and its post-review repairs. PR #36 is now the landed foundation, not the finished recursive/self-learning campaign.

## Scope

Make the repl-researcher's recursive campaign durable, resumable and *self-describing*, and make every self-learning mechanism attached to it (R-Inject wedge, task classifier, CV-1/CV-2, threshold/consolidator, harvest, judges, living-description rolling metrics, traces) consume per-iteration durable evidence instead of one terminal datum per campaign — without inflating any counter by quantum count.

Includes: `execute-repl-researcher-rlm` loop + checkpoint/action events, Phase-2 tree executor + map-each coordinator, sandbox effect primitives, recovery scan, usage/deadline accounting, trace assembly, and the ontology/evaluation consumers of researcher events.

Excludes: GEPA (no call site consumes researcher traces — `components/gepa` has no `get-llm-traces` caller); pattern recording (`docs/PATTERN-RECORDING.md` never touches the researcher; its writer is `:evaluation/trace-evaluated`, no producer found on this path); legacy non-RLM `execute-repl-researcher`; browser-tools (destructured at `rlm_sandbox.clj:317`, never bound in RLM mode).

## Grill decisions

**G1 — Checkpointed execution becomes the default for recursive researchers.** `:checkpointed? false` stays as an explicit escape hatch (legacy path preserved). Blocker: the O(n²) full-history-per-checkpoint write amplification must be fixed before the default flips, or the flip ships a storage regression. Consequence: `ExplicitOptInPreservesCompatibility` (orc-service.allium:325) is re-tended to explicit *opt-out*; every defect that today only affects opt-in users becomes a default-path defect — notably D5 (recovery scan) and D4 (usage/budget atoms).

**G2 — Recovery is automatic, and the obligation is split in two.** Restore the strong wording (`ActiveCampaignsRecoverAutomatically`, "without caller resubmission") and split orc-service.allium:413 into two obligations so the ledger cannot hide the second behind the first: (a) the recovery scan recognises `:repl-researcher` frontiers (`runtime.clj:589`); (b) the scan runs on its own at startup — not an API a caller must remember. Rationale: with G1 every campaign yields, so the started-without-completion window is on the default path; a durability feature whose recovery step is a manual call is a debugging tool, not durability. Consequence: frontier fencing (D6) is pulled into this arc — two booting nodes must not both claim one frontier. DET-E2E-231 becomes an acceptance gate, not an open item.

**G3 — A classification is a per-campaign fact; one campaign is one occurrence.** The wedge is skipped when `:researcher-resume?` is true and the classifier payload is carried forward in the checkpoint. Decisive evidence: `build-task-signature` (task_classifier.clj:547-565) is pure over the immutable tick snapshot, so re-classifying asks an identical question — differing answers are reranker nondeterminism or mid-campaign corpus drift, i.e. exactly the noise that corrupts the counters. Fixed at both ends: producer skips on resume; `:ontology/assign-task-class` becomes idempotent on the occurrence key `[source-sheet-id source-tick-id]` (no guard today, ontology/commands.clj:1408-1453) so no future producer can re-inflate `[:tree-class] :total`, harvest `:min-occurrences`, or the classifier `retrieval-gate`. Explicitly accepted: a campaign whose work reveals a different task is NOT reclassified — model-requested reclassification is a separate feature with its own trigger, not a side effect of resuming.

**G4 — The worked pattern is keyed on outcome and shape, not recency; all evidence accumulates.** CV-2 today (`ontology/todo_processors.clj:292-381`) branches only on DSL equality (`:add`/`:support`/`:edit`) against ONE fixed-literal claim slot per class, never reads `:status`, and its only guard is `(some? generated-tree)`; harvest's `best-recommended-pattern` (`harvest.clj:473-481`) then ranks by `:confidence` with no `:evidence-basis` filter — so a tree that FAILED can be crystallized as the class's proven pattern. Decisions: (i) CV-2 reads `:status` — a successful tree records/reinforces the worked pattern, a failed one records a weakness and never displaces a success; (ii) the claim is keyed per `:tree-fingerprint`, not one-per-class, so multiple working shapes coexist and harvest's coherence axis measures something real; (iii) `best-recommended-pattern` prefers success-backed, occurrence-corroborated claims, enforcing the boundary CV-2's own docstring already states ("a fact about what happened, not a judgement about whether it was good"); (iv) nothing in the description is last-write-wins — the claim system's accumulation (support counts, episodes, anti-recency) is the grain, and CV-2's overwrite slot was the defect against it. No new event fields needed: the bookend already carries `:status` + `:tree-fingerprint` + `:generated-tree` together (`rlm_tree_executor.clj:928-946`). Withdrawn: the earlier proposal to give tree-shape judges a tree-scoped identity — with per-tree status available as fact, per-tree LLM judging is cost for little value. `OneJudgeScorePerCompletion` (evaluation.allium:276-286) stands unamended; the `existing-judge-score?` full-scan → tag-scoped fix (`evaluation/commands.clj:44-58`) remains as hygiene.

**G5 — The occurrence stays the unit of evidence; it carries a bounded iteration digest, and code is part of it.** Today judges receive only `{:inputs :outputs :instruction}` (`judge_runtime.clj:103-131`) — a black box graded by its last output, which is why its strengths/weaknesses are thin. The digest gives judge AND reflection the same material: per iteration, `:iteration :status :duration-ms :tree-fingerprint`, error class + bounded excerpt, var deltas as key lists, bounded `:reasoning`, the Phase-1 `:code`, and the emitted tree INCLUDING its code nodes. What projection strips is data payload VALUES only (`:read-keys`/`:write-keys` + profiles, per `evidence_projection.clj:75-100`) — the 6.4 MB blowup was blackboard data riding `:inputs`→`:writes` and growing within a session, not code; code is kilobytes and does not accumulate. Keeping the occurrence as the unit preserves G3's counting rule so no counter or threshold needs re-tuning. The digest needs its own MEASURED density constant before entering the budgeted window (`consolidator.clj:118-124` — under-prediction is fixed with new anchors, never a bigger constant).

**G6 — Generated code becomes durable source text.** `sanitize-tree-for-events` (`rlm_tree_executor.clj:206-227`) replaces inline `[:fn <object>]` with the literal `"<inline-fn>"` and the real fn lives only in a JVM-local atom cleared at `:881` — so code the model writes inside a generated tree is NEVER durable, v1-vs-v2 comparison is impossible, and a harvested `:recommended-pattern` containing `"<inline-fn>"` ships shape without substance (unrunnable, unlearnable). Persisting source text serves four goals at once: comparable/runnable patterns; D2 (the P0 checkpoint crash) dissolves at the root because source is data, not a function; a resumed campaign can reconstruct the fn after restart; and judge/reflection see code + error + outcome together. **RR-P1 resolved the gate:** already-compiled SCI closures have no recoverable source metadata, while a quoted emitted tree reaches the host as exact data, round-trips through `pr-str` / `read-string`, and compiles its inline functions with `sci/eval-form`. The string-authored fallback is unnecessary; RR-6 implements the quoted-source boundary.

**G7 — Single-owner execution: OPEN, research-gated. Do not settle for at-least-once by default.**

What is already true (verified, do not rebuild): the cross-node fence EXISTS at the platform level — grain `control-plane.allium` CP6 `LeaseFencing` ("at most one node processes a tenant's events at a time") and CP1 `OneLeasePerTenant`, enforced per event by `lease-check-fn` (`todo_processor_v2/core.clj:208-213`); ORC starts the control plane (`bases/orc-dev/core.clj:113-119`). A second ORC-level lease would be duplicated machinery fighting the platform's.

Residual hazard the tenant lease does NOT cover:
1. Intra-node duplicate delivery — the `[revision next-iteration]` CAS rejects the second RECORD, but the provider call already fired before the CAS ran.
2. Lease handoff mid-quantum — nothing interrupts the losing node's in-flight future (`bounded-call` only interrupts; a blocked socket read ignores it). Its late checkpoint is correctly CAS-rejected, so its work is discarded but its tokens are spent.

`ResumeOwnershipIsFenced` (orc-service.allium:408) currently promises reticks and recovery "converge without duplicating provider, tool or child work" — that is FALSE in the handoff window. The spec must not be re-tended until this question is answered, and must not be weakened to fit the code (that is the mistake PR #36 made twice).

Design space under research (two dispatched studies: grain/ORC internal machinery; external durable-execution prior art + provider idempotency reality):
(a) fencing tokens — monotonic epoch on every write, resource-enforced; is one obtainable from the control plane, and can event-store CAS enforce it today?
(b) pre-effect ownership validation — check the lease immediately before each dispatch rather than once per quantum; narrows the window from minutes to microseconds with no new machinery
(c) durable intent -> effect -> completion (outbox/two-phase) — does not prevent duplication but converts an unknown into a detectable known-unknown for recovery to reconcile
(d) graceful handoff / drain — control plane withholds a tenant from B until A has quiesced or its lease has provably expired beyond max effect duration; the only option that ELIMINATES overlap rather than shrinking it
(e) content-derived action identity — replace execution-order ordinals (`executor.clj:2920`) with identity derived from call site + arguments; a correctness fix independent of which fence wins, because ordinal drift can replay a right result into the WRONG call
(f) boundary-owner idempotency — real for our own tools, unreliable for LLM providers (`:orc/idempotency-key` is already dropped before the wire by OpenRouter's allow-list)

Hard constraint to test, not assume: a provider that does not honour an idempotency key cannot be made exactly-once by anything we build. If that holds, the strong mechanism must make the WINDOW provably closed (drain/fencing), not make the provider deduplicate. D7 (identity for inline `(llm ...)`, `mint-behavior!`, deterministic tool ordinals) is load-bearing under EVERY option in the space.

Decision deferred to the research readout; this becomes an Allium `open question` and a HITL slice, not an AFK one.

**G8 — Resume state and the iteration record are separate facts (fixes the G1 blocker).** Today the checkpoint conflates them: `checkpoint-result` (`executor.clj:2966-2978`) writes the ENTIRE history into every `:rlm/researcher-checkpointed`, and the terminal checkpoint embeds `:terminal-result` carrying that history again — a 10-iteration campaign stores history 1..1, 1..2, ... 1..10 (quadratic durable bytes). Split them: **resume state** (`:next-iteration :revision :sandbox-vars :var-creation-times :usage :cumulative-tree-ms :iteration-attempts :campaign-deadline-ms`) stays in the checkpoint, small and overwritten per quantum; the **iteration record** (G5's digest) is written ONCE per iteration and never rewritten. O(n) instead of O(n²). The split is domain-shaped, not a compression trick — mutable current state vs immutable historical fact, different lifetimes, different consumers, different retention.

Consequences: (i) **D9 dissolves** — the trace assembler no longer merges checkpoint history against terminal `:iterations` with checkpoint winning (which today DROPS the richer `:tree-outcome`/`:child-trace-id`/`:child-outcome`), and retries at the same `:next-iteration` stop collapsing last-wins; there is one immutable source per iteration. (ii) G5's digest IS the iteration record, not a projection bolted onto a checkpoint. (iii) Prompt-history reconstruction on resume becomes a read of iteration events rather than a blob carried in state.

Residual, flagged not solved: `:sandbox-vars` is still written in full every checkpoint, so a campaign with a large working set amplifies linearly in sandbox size x iterations. Resume needs real values (the evidence-projection instinct does not apply here). MEASURE before deciding whether it needs delta encoding or a bounded-working-set policy.

**G9 — Map-each survivors are rejoined from durable child completions, not re-run.** `map-each-state` (`todo_processors.clj:3422`) is a `defonce` atom whose own comment states the now-invalid assumption: "Loss on restart is acceptable (the parent tick will timeout and can be restarted)." Under G1 the parent RESUMES, so a restart mid-map-each leaves a child tick with no coordinator — nothing delivers the completion promise, `await-existing-tick` blocks the full `timeout-ms`, then returns `:timeout` and triggers a whole-map retry. Concretely: 27 of 30 chunks done, process dies, we burn the timeout and re-pay for all 30. Advertising resumability while the most expensive thing in the system is not resumable is the defect.

Decision: reconstruct the coordinator on resume from durable child completions (each map-each child is a node execution carrying `::map-each-index` in exec-context, so its completion is already durable and tick-tagged); pending = declared indices minus completed indices. Same pattern PR #36 established at the tree level (`reconstruct-completed-tick`, `rlm_tree_executor.clj:34-70`), applied one level down — no new event types, no spec-level coordinator entity. Riders: dedupe on `[tick node exec-context]` so a retried child at the same index does not create a second slot; `:partial` semantics must survive rejoin — the failure indices and reasons feeding the model's next iteration have to be reconstructed too, or the repair loop loses its input.

**G10 — Recurrence is counted at outcome; abandonment is infrastructure noise, not evidence about a behavior.** Live defect: the wedge emits `:ontology/task-classified` BEFORE the model does any work, and `consolidation-delta-counters` bumps `[:tree-class] :total` on that event (`ontology/read_models.clj:1851-1855`) — so a campaign that classifies and immediately crashes counts toward harvest `:min-occurrences 10` while contributing NO quality signal (no completion, no judge score, no success/failure). Recurrence was counted at intent, quality at outcome. G3 cut this from N counts to one; one is still wrong.

Decisions: (i) move the recurrence bump from classification-time to terminal-time — an occurrence counts toward recurrence only when the campaign reached success, failure, or timeout; (ii) an ABANDONED campaign (crash / unresumed frontier) contributes its iteration records to DIAGNOSIS (the reflection may describe what was tried) but moves no gate; (iii) a FAILED campaign is not abandoned — failure is a verdict: it counts for recurrence, counts against the dimension/consistency axes, and its failed shapes are recorded per G4. Learning from failure is the point; learning from a power cut is not. Accepted consequence: a long-running campaign does not register as an occurrence until it ends, so recurrence lags reality by roughly one campaign duration — correct, since it has not yet produced evidence.

**G11 — Coherence measures WINNING shapes, one per occurrence, and rolls out report-only.** Latent inversion: `distinct-tree-shapes` (`harvest.clj:361-380`) counts fingerprints across EVERY emitted tree while the denominator is campaigns, and a campaign emits one bookend per repair round — so ~10 typical campaigns yield ~25 shapes / 10 occurrences = 2.5 against `max-shapes-ratio 0.5`. Invisible today because the numerator was always 0 (measured 0/138 bookends carried a fingerprint), so `0/n <= 0.5` passed VACUOUSLY. G4 makes fingerprints real, which wakes the gate and immediately blocks everything — and blocks it perversely: a model that recovers well from a bad first tree scores LESS coherent than one that fails outright.

Decision, clarified before implementation: coherence = distinct successful WINNING shapes / successful campaigns. A winning shape is the terminal shape that carried a successful campaign to success. Failed and timed-out campaigns continue to count for recurrence, quality and weakness evidence, but they do not enter either side of the coherence ratio and therefore cannot make a failure-heavy class appear more convergent. The per-campaign repair-round count remains description evidence, not a gate we have no data to calibrate.

Rollout: coherence runs REPORT-ONLY first — `harvest-gate-report` (`harvest.clj:284-336`) already emits per-clause verdicts; compute and log it without blocking until the ratio's real distribution is known, then turn it into a blocker with a calibrated threshold. Rationale: a never-exercised gate made load-bearing fails silently — "harvested nothing for a month" is indistinguishable from "nothing qualified yet."

Note for `/tend`: this is a spec CLARIFICATION, not a change. `ontology.allium:1038-1076` requires `distinct_shape_ratio(tree_class) <= maximum_shape_ratio` but never pins whether the ratio is over all trees tried or the ones that won. Also record that a fingerprint is a SHAPE, not a pattern: `rlm_fingerprint.clj:35-57` normalizes `:fn` and `:instruction` to placeholders, so two trees differing only in generated code share a fingerprint — which is right for convergence, and means G4 per-fingerprint claim keying is coarser than "the same tree."

**G12 — The live stream becomes a projection of the durable iteration record; there is one account of a campaign.** Today two parallel paths exist and neither survives the arc: ephemeral emits (`:rlm-iteration-started`, `:rlm-code-generated`, `:rlm-sandbox-completed`, `:rlm-phase2-started` — `executor.clj:3186-3432`, `rlm_tree_executor.clj:751`) that no-op without a live subscriber and store nothing, and durable-but-terminal-only `:rlm/tree-generated` + `:rlm/researcher-iterations` (both emitted once at campaign end, `todo_processors.clj:2285-2321`, inside the non-`:running` branch). Mid-campaign there is nothing durable to look at; after a restart the live view is gone (`streaming/link-child!` lineage is a process-local atom, `streaming.clj:87`, and a rejoined child skips lineage linking entirely). The two writers have already drifted — the `:rlm/tree-generated` docstring claims it fires per `emit-tree!` when it fires once per campaign.

Decision: once G8's iteration record exists, it is the single source; the live stream is a PROJECTION of it — subscribers tail durable iteration events rather than receiving separate ephemeral emits. Rationale tied to stated intent: the loop must analyze ITSELF, and self-analysis can only read durable events; anything living only in a live stream is invisible to the mechanism it is meant to feed. One account, seen identically by the learning mechanism and by a human watching.

Riders: (i) intra-iteration progress finer than one iteration (token streaming, "sandbox is running") stays ephemeral — genuinely a preview, correctly not durable; (ii) `:rlm/researcher-iterations` becomes redundant and is RETIRED rather than maintained as a second terminal-only copy — it has no production consumer today (dev/bench/tests only); (iii) rejoined children must link lineage on the replay path too, or the projection has holes exactly where a restart happened.

**G13 — A harvested behavior is advice the model authors from, and its pattern must be genuinely adoptable.** R-Inject prepends a text block ("## Suggested patterns from corpus") with capabilities/strengths/weaknesses/`:avoid-when` plus the worked pattern DSL, and names four moves — ADOPT / ADAPT / SPECIALIZE / MINT (`todo_processors.clj:1390-1465`). There is no executable path: the sandbox has `mint-behavior!` (write) and `get-description` (read), nothing that RUNS a behavior. So the loop closes as advice, which is correct — the prompt's own framing ("the corpus is evidence, not gospel") is right, and executable invocation would freeze shape and fight the judgment that makes the researcher better than a fixed pipeline.

The defect: **ADOPT is currently impossible for any pattern containing inline code.** The corpus instructs the model to adopt a pattern whose `:fn` slots read the literal `"<inline-fn>"` (G6) — a placeholder where the logic was. The model cannot emit that tree, so the corpus's own top-recommended move silently degrades into "reconstruct from scratch and hope" — the ReACT cold-start failure reappearing exactly where the corpus was meant to prevent it.

Decision: keep the model as the author of every tree; make the pattern it is shown actually runnable — real source instead of `"<inline-fn>"` (G6), plus declared key bindings (what the pattern reads and writes) so "this shape, my keys" is a mechanical rebind rather than a re-derivation. Do not advertise a move the artifact cannot support. Executable behavior invocation is explicitly NOT taken now; if it is ever wanted it must first solve slot rebinding, which a proven tree does not declare today.

This gives G6 a second independent reason to be non-negotiable: without durable source, the corpus's headline recommendation is broken by construction.

## Research findings (established facts, not decisions)

**R1 — No LLM provider supports idempotency keys for completions.** Verified: 0 occurrences of "idempotency" in OpenAI's official 2.97 MB OpenAPI spec; none in Anthropic's docs corpus; OpenRouter's `X-OpenRouter-Idempotency-Key` is OUTBOUND WEBHOOK dedup, not request dedup. Azure OpenAI and Vertex: none. AWS Bedrock has `clientRequestToken` on the ASYNC job APIs only (`StartAsyncInvoke`, `CreateModelInvocationJob`), not on `InvokeModel`/`Converse`. TRAP: the OpenAI and Anthropic Python SDKs both contain complete Stainless idempotency plumbing with `_idempotency_header = None` never reassigned — dead code that reads like support. Both SDKs retry 5xx twice by default with NO dedup key, so a generation whose response was lost is re-run and re-billed. CONSEQUENCE: `:orc/idempotency-key` must stop being described as provider deduplication anywhere in code, docs, or spec; it is useful only at OUR boundary (recognising an already-dispatched call on resume).

**R2 — Every durable-execution engine is at-least-once for side effects.** Temporal ("at least once by default... at most once if retries are disabled"), Restate (journal-after-execute leaves the window open for `ctx.run` bodies), DBOS (exactly-once only for TRANSACTIONAL steps sharing the Postgres txn), Azure Durable Functions (verbatim: "If a failure occurs after the activity completes but before the result is recorded, the runtime might rerun it"), Step Functions (the "exactly-once" claim scopes to WORKFLOW execution / state re-entry, not the callee). AWS's Durable Execution SDK is the most honest: "Both semantics are per retry attempt. Neither guarantees the step runs exactly once across the entire workflow" — and exactly-once is purchased with at-most-once + no-retry, i.e. may-not-run-at-all. Azure documents our exact hazard with a number: ~10 s to detect lease loss, "Any orchestration instances that belong to this partition may temporarily observe duplicate execution of activities" (split-brain).

**R3 — Fencing requires the RESOURCE to check the token (Kleppmann).** A lease's expiry is enforced at the lock service, not the resource; an arbitrary pause (GC, network delay — documented at 90 s at GitHub) between check and write defeats it. A pre-effect lease check does NOT fix this: it is TOCTOU and the pause can occur inside the gap. Requirement: (a) monotonically increasing tokens, (b) holder attaches token to every request, (c) **resource persists the highest token seen and rejects lower** — miss (c) and it is decoration. Production implementations: Chubby sequencers (lock generation number, validated by the downstream server), Kafka producer epochs, HDFS JournalNode epochs.

**R4 — Exactly-once for an external effect is available exactly when the callee participates.** Kafka achieves it because the effect target IS Kafka (broker checks producer epochs); Confluent states the boundary: "if the processing has side effects on other storage systems, the APIs covered here are not sufficient." Our four effect types split accordingly: Phase-2 child trees (callee = us, our tick ids) -> exactly-once achievable; checkpoint-safe tools (callee = our services) -> exactly-once achievable; `mint-behavior!` (callee = our ontology, derived id already stable) -> exactly-once achievable; LLM provider call (callee does not participate) -> at-least-once, irreducibly.

**R5 — Nobody drains on proof of quiescence.** Only cooperative cancellation (Temporal `WORKER_SHUTDOWN`, Kafka `onPartitionsRevoked`, Azure "immediately stop reading messages") which a partitioned or GC-paused worker skips entirely, or a timeout (DBOS Conductor 60 s executor timeout; Azure ~10 s). The one mechanism designed explicitly AS a fencing substitute is Chubby `lock-delay` (~60 s) — for "file servers that do not support sequencers," refusing to re-grant a lock long enough for a zombie's effects to drain. Burrows labels it the inferior fallback to sequencers. TTL guidance is consistent across vendors and is best-practice not guarantee: the ownership timeout must EXCEED worst-case work duration, or a healthy worker manufactures the split-brain you are trying to avoid.

**R6 — Grain exposes no fencing token, and its CAS cannot reach one.** Lease events carry only `{lease/node-id, lease/tenant-id}` — no epoch, term, or expiry (`control-plane/events.clj:8-29`); staleness is evaluated at READ time (heartbeat 5 s, threshold 15 s = 3 intervals). Lease handoff is `(reset! tenant-ids-atom ...)` and nothing else (`control-plane/core.clj:117-124`) — no drain, no quiesce, no cancellation; in-flight work continues. CAS predicates are stamped with the append's own tenant and cross-tenant reads are forbidden (`protocol.clj:71`), so a domain-tenant CAS structurally CANNOT read lease state. CONSEQUENCE: a fencing token must be minted by ORC into ORC's own stream — a per-frontier claim epoch for `[tick node]`, CAS'd on "no higher claim exists" — which is arguably better than a per-tenant lease epoch because it is scoped to the exact contended resource and needs nothing from the platform.

**R7 — ORC has no fence wired at all today.** `start-tenant-poller` does not even ACCEPT `:lease-check-fn` (`todo_processor_v2/core.clj:495-510`); only `start-polling` does, and it has no call sites. So `process-event`'s ownership guard (`:211-213`) short-circuits on nil and processing always proceeds. The `LeaseFencing` contract `todo-processor-v2.allium:194-206` declares it DEMANDS is never supplied in the deployed wiring. Additionally the researcher's future (`todo_processors.clj:2086`) is never registered with `execution-budget/register-work!` (leaf nodes are, `:1848`), so the one existing cancellation mechanism cannot reach it. CP6's conformance test calls `process-event` twice SEQUENTIALLY in one thread with a no-op handler — it is a checkpoint-dedup test, not a mutual-exclusion-over-effects test.

**R8 — Content-derived identity must be generated INSIDE the durable step.** AWS, verbatim: "Generate the key inside a step. A key generated outside a step changes on replay, which defeats deduplication and doubles up on retry." Temporal's equivalent is `workflowRunId + '-' + activityId`. Our current `action-ordinal` is execution-order dependent and reset per iteration, and `retry-result` re-runs the SAME iteration number with the ordinal reset to 0 — minting identical `.../N/tool/1` ids for what may be a different call (silent replay poisoning). `stable-tick-id` (`executor.clj:3689-3695`) already demonstrates the correct digest pattern via `nameUUIDFromBytes`, and `commands.clj:1297` already hashes `action-id` the same way — so action-id can become an opaque content digest with ZERO schema change.

**G14 — Blocking stays terminal, but a blocked child becomes RECORDED and rejoinable.** Unlike G2, this weakening is honest: there is no unblock or approval-resume command anywhere in ORC; the opaque `:block-payload` (WS-2a) propagates to the caller and the host decides, and a blocked root is terminal everywhere in the engine. Ratify `BlockedChildPreservesPriorProgress` (orc-service.allium:397-401) as written.

Fix the defect underneath: `persist-action!` records only `#{:success :partial :failure}` (`executor.clj:3712-3714`), so a blocked child's work is never durable as an action. Consequences closed by this decision: (i) a re-run currently RE-EXECUTES the blocked child — if the block was an approval request, a human is asked twice; (ii) the block reason never becomes campaign evidence, so the loop cannot learn "this class blocks on X", which is exactly the `:avoid-when` a behavior should carry. Decision: persist the blocked action, make the child rejoinable, and carry the block reason into the iteration record as evidence.

### DEFERRED CAPABILITY — durable human-wait frontier (do not lose this)

Recorded as an Allium `open question` on orc-service.allium so it stays visible rather than being quietly dropped. What a pause-for-approval frontier would need, and what is BLOCKED on it:

Prerequisites this arc does NOT provide:
- An approval identity and lifecycle (who may approve, what they are approving, one-shot vs revocable) — no such entity exists in any spec today.
- A wait-state that is distinct from `:running` and from terminal `:blocked`, with its own transitions and its own projection.
- Deadline semantics for a waiting campaign. DIRECT COLLISION with G7/`CampaignDeadlineSurvivesRecovery`: the campaign deadline is deliberately ABSOLUTE and survives yield, retick and restart. A campaign waiting three days for a human blows it. Either waiting time is excluded from the campaign clock (which breaks "absolute"), or approval must arrive inside the campaign budget (which makes the feature useless for real human latency). This is the hard design question and it is NOT answerable inside this arc.
- Resume-the-same-child semantics: approval must resume THAT child under THAT logical action id, which needs the claim-epoch machinery from G7 to already exist.

What is blocked on it (i.e. things we are consciously NOT getting):
- HITL steps inside a generated tree. Today a tree that needs human input can only terminate the campaign; the host must start new work and the model loses its sandbox state and its reasoning context.
- Long-running approvals as a first-class researcher capability (compliance sign-off, spend approval, publish gates).
- The ontology EV-8 review-case lifecycle noted the same absence independently ("no durable human-wait/resume frontier in the canonical root") — so a future arc should solve this ONCE for both, not twice.

Why deferring is safe: a blocked campaign is structurally just a campaign whose next quantum is gated on an external event rather than a timer, which is precisely what this arc's checkpoint + resume machinery provides. G14's recording work makes B strictly EASIER later (the blocked action is already durable and rejoinable); it forecloses nothing.

**G7 (RESOLVED) — Five-layer fence; the strong mechanism is relocated to where it is achievable.** Grounded in R1-R8: exactly-once for the LLM provider call is not buildable by anyone (no vendor participates), Kleppmann's requirement (c) needs the RESOURCE to check tokens, Grain exposes no token and its CAS cannot read the lease tenant, and ORC has no fence wired at all today.

Layers:
1. Wire `lease-check-fn` (3 lines; `start-tenant-poller` does not currently accept it). Fences DISPATCH. Necessary, insufficient.
2. **Per-frontier claim epoch in ORC's own stream** — monotonic per `[tick node]`; every durable write CASes on it. Our event store becomes the token-checking resource, satisfying Kleppmann (c) in the only role we can fill. Scoped to the contended resource rather than a whole tenant, and needs nothing from the platform. -> GUARANTEES exactly-once campaign state; a zombie's result can never land.
3. **Claim-before-effect with content-derived identities** — every stable logical-action preimage contains `(tick, node, iteration, kind, target, canonical request/args)` and deliberately excludes attempt/order. Actions originating in generated code additionally include that durable source hash. Each physical dispatch has a distinct attempt identity derived from the logical identity, epoch and attempt ordinal. Racing nodes compute the SAME logical key, so the loser's CAS predicate rejects BEFORE firing. A checkpoint-safe effectful tool participates through the context-aware three-argument caller and deduplicates the stable key; a caller that cannot receive that context is rejected before claim or dispatch. Two-argument compatibility remains only outside this checkpointed effect boundary. -> GUARANTEES exactly-once generated children, participating checkpoint-safe tools, and behavior mints (R4: the callee participates).
4. **Durable intent for provider calls** — the outer provider action that produces code is keyed by its canonical request/module inputs and provider/model target, never by its not-yet-produced response. Every indeterminate call becomes a queryable object, not a silent mystery.
5. **Drain** — register the researcher future (it is not registered today, `todo_processors.clj:2086` vs leaf nodes at `:1848`), cancel on lease loss, Chubby-style delay before reassignment. Explicitly labelled PROBABILITY REDUCTION, not guarantee (R5: a partitioned or GC-paused worker skips cooperative drain entirely).

**Unification (the key refinement): the intent record and the claim are the SAME append.** `{logical-action-id, attempt-id, epoch, attempt-ordinal, request-hash, status: dispatched}` CAS'd on "no higher epoch has claimed this logical action" is simultaneously the fence (layer 3) and the detectability record (layer 4). No extra write amplification, and because the claim is per EFFECT rather than per quantum, a zombie's spend is bounded to at most one in-flight effect instead of a whole quantum's worth.

**RR-P2 resolved the store feasibility gate, with a dependency-audit correction.** The initial action-tag-only predicate was falsified: it allowed same-epoch duplicate claims and let a stale owner claim a previously unseen action after the frontier advanced. The corrected tenant-local predicate scopes to a shared campaign tag and reduces the frontier plus effect facts in one pass. On the real in-memory, SQLite and Postgres v3 stores it rejected stale new-action claims, stale outcomes, and same-epoch duplicates before append; 50/50 simultaneous same-action/same-epoch races per backend produced exactly one claim and one conflict. Postgres exercised its per-tenant advisory lock, predicate read and append in one transaction. Corrected median CAS overhead was 0.048 ms in memory, 0.631 ms on SQLite and 0.845 ms on local Postgres; these are feasibility measurements, not SLOs. The action-scoped predicate and earlier measurements are withdrawn.

**Invariant replacing the false `ResumeOwnershipIsFenced`** (which today promises "converge without duplicating provider, tool or child work" — false in the handoff window):

> Exactly-once campaign state and exactly-once generated-child, checkpoint-safe-tool, and behavior-mint effects. Provider calls are at-least-once, bounded by the number of ownership epochs a quantum crosses, and every indeterminate call is durably recorded and attributable to the epoch that produced it.

**ADR at grill-end** (meets all three tests: hard to reverse, surprising without context, real trade-off): record WHY exactly-once external effects was rejected as unbuildable, with the provider evidence from R1 and the callee-participation boundary from R4, so it is not re-litigated in six months.

**G15 — Quantum hold time becomes bounded and recorded (waste-bounding, not correctness).** Facts: the classify wedge measured 302 s and runs OUTSIDE the campaign clock (`campaign-started-at-ms` set at `executor.clj:2939`, AFTER the wedge at `todo_processors.clj:2114-2126`); `bounded-call` uses `future-cancel` (interrupt-only, cannot stop a blocked socket read); NO HTTP transport timeout is set anywhere in this repo (`llm/core.clj` has none — it lives in external `litellm-clj`); default provider ceiling is 900 000 ms.

Correction to an earlier framing in this grill: the 15 s staleness threshold governs HEARTBEATS, and the heartbeat runs on its own 5 s timer independent of the work — a busy node is NOT declared dead mid-quantum. The real number is the OVERLAP WINDOW = staleness detection (~15 s) + remaining duration of the in-flight effect (up to 15 min).

With G7 settled this is NOT a correctness problem — claim-epoch CAS means a zombie's result can never land regardless. It is about bounding WASTE and making G7 layer 5 implementable: a drain delay sized above P99 quantum duration is unimplementable when P99 is unbounded.

Decisions: (i) the wedge gets a deadline and joins the campaign clock; (ii) real transport-level timeouts on provider and tool HTTP so cancellation is not purely advisory; (iii) max quantum hold becomes a COMPUTED, RECORDED number so the drain delay has something real to size against; (iv) extend the existing shortest-applicable-deadline clamp (`phase2-remaining-ms`, `executor.clj:3598-3609`) to the provider call and the wedge — it is nearly free there. Explicitly NOT built: a general worst-case-duration predictor. We lack the data to predict, and R5's vendor guidance cuts the other way — a too-aggressive bound manufactures the split-brain it is meant to prevent.

**G16 — Indeterminacy policy splits by callee participation; provider re-calls are absorbed, not surfaced to the model.** On resume a claim with no recorded outcome means the effect may or may not have happened (R1: the in-flight case is undocumented at every provider; even Stripe refuses to dedupe a concurrent duplicate and returns 409).

Policy by effect type, following the R4 boundary:
- **Phase-2 child tree** (callee = us, content-derived tick id): REJOIN via `await-existing-tick`. Never re-run.
- **Checkpoint-safe tool** (callee = our services, honours the key): RE-CALL with the same idempotency key through the required context-aware three-argument caller; the tool dedupes. A caller that cannot receive the key is rejected before claim or dispatch. Safe by contract.
- **`mint-behavior!`** (callee = our ontology, derived id): RE-CALL; the derived id makes a second mint idempotent.
- **Provider call** (callee does not participate): RE-CALL, and **absorb it** — see below.

Provider decision and rationale: treating an indeterminate call as a FAILURE, or surfacing it to the model as "outcome unknown", both violate G10's principle. An indeterminate call is infrastructure noise, not a verdict about the model's work — the model did not fail, our process died. Feeding it into the reasoning history teaches a false lesson about the model's own competence, and surfacing it additionally asks the model to reason about our infrastructure, which is not its job.

Therefore: re-call, and make the re-call INVISIBLE to the model's reasoning history. It is a second ATTEMPT of the same logical action, not a new iteration — one action identity, multiple attempts, each attributable to the epoch that made it. This is already the spec's language for children ("Each attempt remains separately traceable", orc-service.allium:369-372), applied consistently. The model's prompt shows one iteration; the iteration record shows two attempts and flags the indeterminacy for operators.

Mechanically free under G7: the new owner claims under a HIGHER EPOCH, which supersedes the orphaned claim and authorises the re-call. No new machinery.

Accepted cost, stated plainly: one duplicate generation per ownership transition per in-flight call, fully attributed and measurable. That is the irreducible price established by R1-R4, and it now appears as a line item rather than as mystery spend.

**G17 — The LLM-call budget becomes durable-derived with an in-memory cache; usage double-counting fixed.** What survives a restart today: campaign usage tokens (`:usage` in the checkpoint) YES; tick-level usage aggregate (`tick-usage` defonce atom, `todo_processors.clj:88`) NO; the LLM CALL COUNT that the budget enforces (`tick-llm-counts` defonce atom, `:54`) NO. So a campaign resumed in a fresh JVM gets a FRESH budget, making `SharedLlmCallBudget` (orc-service.allium:1097-1102 — "Once exhausted, no branch can make a further provider call") false across exactly the restart this arc introduces; G1 makes it a default-path falsehood.

Decision: durable claims are the source of truth (G7 already makes every provider call a claim event, so the ledger exists), with the atom retained as a HOT CACHE rebuilt on resume. This extends a proven idiom rather than inventing one — `reserve-llm-call-or-cancel!` (`todo_processors.clj:141-182`) already pairs a process-local claim with a durable status recheck and documents why BOTH are required.

Why checkpointing the counter alone is insufficient: the budget spans a TRACE FAMILY — the spec counts "recursive researcher iterations, inline researcher primitives and descendant generated-tree leaves." A child tree's LLM leaves run in their own ticks, so their calls are not in the parent's checkpoint. Lineage IS durable (`:parent-tick-id` + the `[:parent-tick ...]` tag, `commands.clj:1051-1112`), so a family count is derivable from events but not from any single checkpoint.

Second, independent bug fixed in the same slice: `add-usage!` runs at `todo_processors.clj:2239` BEFORE the `:running` check at `:2273`, and the researcher returns CUMULATIVE usage in every `:running` result — so an N-quantum campaign contributes ~N*u1 + (N-1)*u2 + ..., quadratic over-counting at tick level. Fix: move `add-usage!` inside the non-`:running` branch, or have `:running` results carry a per-quantum delta. One-line class of bug that silently corrupts every cost number the loop reports.

MEASURE, not assumed: the cost of the family-walk read at scale is unknown — measure before deciding whether the cache is warmed eagerly or lazily. The correctness answer does not depend on it.

**G18 — Retention is two policies, because checkpoints and iteration records are different kinds of thing. Structure locked now; numbers measured.**

Structural decisions (decidable from the domain, locked):
- **Checkpoints are SUPERSEDED.** Only the latest per `[tick node]` is load-bearing, and under G7 that is now PROVABLE — an older checkpoint carries a superseded epoch. Compaction of older checkpoints is therefore safe by construction, not by convention.
- **Iteration records are NOT superseded.** Immutable evidence; that is their entire job. Their retention is an evidence-policy question, not a storage-hygiene one.
- **Sandbox state is delta'd with periodic full snapshots.** `:sandbox-vars` is written in full on every checkpoint today — linear in sandbox size x iterations even after G8 fixes the history quadratic. But `:vars-created` / `:vars-updated` are already computed every iteration, so THE DELTA IS ALREADY KNOWN. Carry only what changed and fold on resume, with a full snapshot every K iterations to bound fold fragility (one missing event must not silently produce a wrong sandbox). Consistent with G8, which already made resume a multi-event read.

Deliberately NOT decided now — the numbers (K, retention windows). `evidence_projection.clj:6-24` records what happened the last time someone guessed: 178 observations x ~36 KB = 6.4 MB, provider rejected the call outright. The density constants are documented as MEASURED, with the explicit rule that under-prediction is fixed with new anchors and never a bigger constant. Picking K or a retention window without measuring real campaigns repeats that mistake with better intentions.

Therefore: "measure sandbox growth and iteration-record volume on real campaigns" is an EXPLICIT DELIVERABLE of the whole-spec integration slice, not a vague follow-up, and the resulting numbers land in the spec as config.

## Post-grill correction — the campaign was never modelled

`allium plan` exposed a real miss in the tend: the ratified decisions were written as prose `@invariant` blocks on `CheckpointedResearcherExecution`, and prose invariants generate NO test obligations. The whole contract collapsed to 3 `contract-signature` obligations — so `/propagate` would have seeded nothing and `/inspect-orc`'s obligation audit would have been decorative for exactly the work that matters. Root cause: invariants were written about a campaign, its iterations and its effect claims, but the spec had no such entities to quantify over (only `WorkflowExecution`, `NodeExecution`, `DelegateInvocation`). The tend skill's own guidance warns against this — do not add detailed rules to an entity that has no transition graph yet.

Fixed by modelling what a campaign actually is, following the `DelegateInvocation` precedent already in the file:
- `Campaign` — `running -> yielded -> running -> success | failure | timeout | blocked | cancelled | abandoned`. `cancelled` is a deliberate terminal infrastructure outcome with retained evidence; `abandoned` is an unresumed frontier with no completion. Neither is a behavior verdict or learning-gate occurrence.
- `CampaignIteration` — the G8 iteration record: index, attempt ordinal, status, duration, shape, and whether code and tree were recorded. Immutable once written.
- `EffectClaim` — stable logical action identity, distinct physical attempt identity/ordinal, ownership epoch, kind, `claimed -> completed | indeterminate`. Both resolutions are terminal: a later dispatch is a new attempt/claim under a newer epoch while remaining recognisably the same logical action.

The current reconciled model adds a cancellation witness plus separate logical-action and physical-attempt constraints. Its fence obligations include `OneClaimPerLogicalActionIdentityPerEpoch`, `EffectAttemptIdentitiesAreUnique`, `EffectAttemptIdentityMatchesLogicalAction`, `OneIterationRecordPerAttempt`, `ClaimsNeverExceedTheirCampaignsEpoch`, `AbandonedCampaignsRecordNoVerdict`, `CancelledCampaignsRecordCause`, and `SuccessfulIterationsRecordTheirCode`. Failed iterations separately record whether code existed, because provider failure can settle an attempt before code generation.

Result at the historical grill base: total obligations 192 -> 265, a delta of 73. The issue files originally contained 75 obligation references but only 49 distinct IDs; those are separate counts and must not be described as 75 unique campaign obligations. After rebasing onto merged main and reconciling cancellation plus attempt identity, the current ORC-service plan is 275 obligations. Across all twelve specs the baseline is 142 diagnostics (0 errors, 35 warnings, 107 info) and 0 analyse findings. `/propagate` has a real campaign ledger, while prose-only decisions remain explicitly identified rather than implied covered.
